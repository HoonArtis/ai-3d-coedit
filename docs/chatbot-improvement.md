# 챗봇 고도화 기록 (2026-10-15)

같은 로컬 모델(qwen3:4b, Ollama 0.40.4, RTX 3080 Ti)로 학생 요청을 얼마나 맞게 처리하는지 평가 문항으로 재고, 고친 뒤 다시 재는 식으로 진행했다. 모델은 바꾸지 않았다. 점수가 오른 것은 모델이 볼 정보를 정리하고, 모델이 할 일을 줄이고, 정답이 정해진 판단을 코드로 옮긴 결과다.

## 한눈에 보기

|---|---|---|---|---|
| 0. 시작 | 씬 JSON을 학생 메시지 자리에 넣던 원래 구성 | 18/20 | 42/60 | 632ms |
| 1. 씬 위치 | 씬을 시스템 메시지로 옮기고 한 줄에 물체 하나 | 18/20 | 47/60 | 596ms |
| 2. 규칙 추가 | 계산·대상·생성 규칙과 예시 | 19/20 | 48/60 | 1,578ms* |
| — | 평가를 109문항으로 확장(세 기능 17·실사용 32 추가), 세 기능 구현 | 18/20 | 75/109 | 2,003ms |

- 세 기능 문항(어울리게 배치·만들기·추천, 17개): 한 번에 고르기 12/17 → 두 단계 15/17 → 코드 검사 16/17.
- \* 2단계의 지연 증가는 같은 시간대 다른 GPU 작업과 겹쳐 원인을 확정하지 못했다.
- 109문항 표의 점수는 모두 현재 채점기로 다시 채점한 값이다(`tools/llm-eval/regrade.ts`). 채점기 수정 내용은 아래 "평가 도구"에 있다.

## 단계별로 오른 이유

### 1. 씬 데이터를 시스템 메시지로 옮김 (42 → 47/60)
원래는 씬 전체를 JSON 덩어리로 만들어 학생 메시지 자리(user)에 "신뢰하지 않는 데이터"라는 안내와 함께 넣었다. 4B 모델은 이것을 학생이 한 말로 받아들였다. 답변에 "신뢰하지 않는 씬 데이터를 확인했어요"를 되읊고, 프롬프트 예시의 "고래 모양 벤치"를 그대로 생성 요청으로 냈다.
씬을 시스템 메시지 끝으로 옮기고, 물체를 `c1 "의자" [내 것] asset=chair 위치(2, 0, 0)…`처럼 한 줄씩 적었다. 현재 선택, 카메라 중심, 되물음 여부는 문장으로 적었다. 학생 말과 데이터가 섞이지 않게 되자 예시 누출과 "여기" 무시가 줄었다.

### 2. 규칙과 예시 추가 (47 → 48/60, 효과 작음)
"오른쪽 1m는 현재 위치 + 1", "45도 돌려는 현재 회전에 더함", "키만 1.5배는 Y만" 같은 계산 규칙과 예시를 넣었다. 일부는 맞게 됐다. 그러나 예시가 다른 문항으로 번졌다. "키만" 예시 때문에 "두 배로"·"반으로"까지 Y축만 바꿨다. 순증은 1문항이었다.
**교훈:** 작은 모델에 규칙을 계속 더하는 방식은 한계가 있다. 이 결과가 3·4단계 방향을 정했다.

### 3. 두 단계 분류 (75 → 79/109, 세 기능 12 → 15/17)
한 번 호출로 도구 27개와 모든 규칙을 읽던 것을 둘로 나눴다.
- 1단계는 문장을 배치·편집·만들기·추천·조회·되돌리기·그 밖 중 하나로만 분류한다. 7개 중 하나를 고르는 쉬운 문제다.
- 2단계는 공통 규칙에 그 분류의 규칙과 도구(1~9개)만 더해 보고 결정한다. 모델이 낼 수 있는 출력 형식도 그 도구로 좁힌다.

오른 이유는 세 가지다. 모델이 한 번에 볼 규칙이 줄어 서로 번지지 않는다. 다른 분류의 도구를 고를 수 없다(만들기 요청에 배치 도구를 내는 실수가 사라짐). 프롬프트가 짧아져 오히려 빨라졌다.
분류 예시를 한 번 보강했다(v1 75 → v2 79). "하나 더"는 편집, "심어줘·채워줘·~느낌 나게"는 배치, "찾아"는 조회, "취소"와 "다시"는 구별. 만들기 프롬프트의 재텍스처 예시가 "고래 모양 벤치"에 그대로 복사되는 누출도 예시를 빼서 막았다.

**함정:** 처음 실행은 문항당 18.7초였다. 분류 호출과 결정 호출의 `num_ctx`(4,096 / 16,384)가 달라 Ollama가 호출마다 모델을 다시 올렸다. 같은 값으로 맞추자 1.6초가 됐다. 서버에서 이미지 프롬프트 정리기도 같은 모델을 다른 설정(4,096, CPU)으로 부르므로 같은 재적재가 일어날 수 있다. 서버 PC에서 확인이 필요하다.

### 4. 정답이 정해진 판단을 코드로 (79 → 91/109, 기존 20문항 만점)
남은 오답 상당수는 모델이 판단할 필요가 없는 것이었다. 이를 모델 앞뒤의 코드(`apps/llm/src/guards.ts`)로 옮겼다.
- **전처리:** 선택이 없는데 "이거/저거/선택한"이면 모델을 부르지 않고 바로 되묻는다. 정확하고, 호출을 하나 줄여 빨라진다.
- **후검사:**
  - 남의 물체를 바꾸는 동작이 하나라도 있으면 전체를 거절하고 이유를 안내한다.
  - 씬에 없는 대상을 가리키면 실행하지 않는다.
  - 새 ID가 기존과 겹치면 새 ID를 주고, 같은 요청 안의 참조도 바꾼다.
  - 복사본을 다시 복사하는 체인은 원본 복사로 고친다.
  - 문장의 개수("세 개", "6개")만큼 생성·복제를 채운다.
  - scatter는 바닥에 두고, "여기/근처"면 카메라 중심 ±2m로 잡는다.
  - 되돌리기에 모델이 지어낸 순번(서버가 거부함)을 지운다. "다시/살려"는 redo, "취소/되돌려"는 undo로 맞춘다.
  - 금칙어 생성을 거절한다. 서버 필터와 같은 규칙을 `packages/contracts`로 옮겨 함께 쓴다.
  - 새로 만드는 도구에 기존 ID를 넣었고 문장에 새로 놓을 말이 없으면 "기존 물체 다시 놓기"로 읽는다.

검사를 넣는 과정에서 한 번 거꾸로 갔다(v2 89). "기존 ID를 넣은 생성 도구는 다시 놓기"라는 규칙이 "의자 6개 둘러놔"까지 바꿔 버렸다. 개수나 "놔/뿌려/심어" 같은 말이 있으면 바꾸지 않도록 고쳐 91이 됐다.

## 함께 만든 기능 (점수의 바탕)
- `arrange_nicely`: 어울리게 배치. 의자는 탁자를 둘러 탁자를 보고, 벤치는 나무 앞, 화분은 탁자 위. 좌표는 `packages/placement/src/arrange.ts`가 계산한다.
- `recommend`: 어울리는 에셋 추천. 빠진 짝을 라이브러리에서 먼저, 없으면 생성 아이디어로 3개를 고른다. 채팅에 [놓기]/[만들기] 버튼으로 보인다.
- "어울림" 규칙은 `relations.ts` 한 곳에 두고 배치와 추천이 함께 쓴다.
- 생성 요청의 채팅 문구를 "완료했어요"에서 "생성 패널에서 확인해 주세요"로 바꿨다.
- 텍스처 단계에 학생 원문(한국어) 대신 영어 정리본을 넘긴다.

## 평가 도구
- 문항(`tools/llm-eval/`): `focus` 세 기능 17, `basic` 기존 20, `student` 말투 40, `real` 실사용 32. 문항마다 모범 답을 두고 채점기 자체를 테스트한다(`tests/llm/eval-cases.test.ts`).
- 연습장 채점(`simulate.ts`): "이쁘게 배치해줘"처럼 정답 좌표가 없는 요청은 서버와 같은 코드로 씬 복사본에 적용해 본 뒤, 겹침·남의 것·삭제·변화 여부로 채점한다.
- 실행: `npx tsx tools/evaluate-llm.ts --suite all [--routing single] [--no-guards]`. GPU 여유가 6,000MiB 미만이면 시작하지 않고, 끝나면 모델을 내린다.
- 재채점: `npx tsx tools/llm-eval/regrade.ts <결과.json> --fails`.
- 채점기 수정 한 건: 추천(recommend)은 씬을 바꾸지 않는데 "씬 변경"으로 채점하던 것을 고쳤다. 109문항 표의 값은 모두 고친 채점기 기준이다.
- 원본 결과: `docs/evidence/llm-eval-runs/`, 단계별 세부: `docs/evidence/llm-evaluation.md`.

## 남은 과제 (18문항)
- 상대값 산수와 대상 혼동: "의자2"를 c1로, 앞/뒤 축, "키만 1.5배". 계산을 코드로 옮길 대상이다.
- 묘사로 고르기: "큰 나무만", "제일 왼쪽 거". 크기·위치로 대상을 고르는 코드가 필요하다.
- 만들기 요청에 재텍스처를 쓰는 오분류 1건. 후검사 규칙으로 고칠 수 있다.
- 개수가 없는 "채워줘·여기저기 놔줘".
- 다음 단계는 "연습장 확인 → 다시 계획" 루프(`ChatAgent`에 붙임)와, 한 문장에 의도가 둘인 요청 나누기다.
- 실제 서버·화면 확인은 아직이다. 서버 PC에서 pull → npm ci → build → 워커 재시작으로 반영한다.
