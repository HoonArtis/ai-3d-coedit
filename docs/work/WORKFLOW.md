# 실행 티켓의 검증·수정 절차

원본 규칙: [CLAUDE.md](../../CLAUDE.md). 실행 목록: [PLAN.md](PLAN.md).

## 작업 단위와 상태

플랜은 전체 범위, 9개 태스크는 모듈 책임, 137개 실행 티켓은 독립적으로 결과를 검증하는 단위다. 이전 37개 ID는 `split`인 분할 이력이며 진행률에서 제외한다. 티켓 수는 이후 범위 변경 시 인덱스와 함께 갱신한다.

상태는 `todo → doing → review → done`이다. `doing` 안에서 현재 단계를 `준비`, `구현`, `검증`, `수정`, `사례 조사`, `재검증`으로 기록한다. `review`에서 결함을 발견하면 `doing`으로 되돌린다. 실제 외부 차단은 `blocked`, 사용자가 범위에서 제외한 것은 `deferred`로 기록한다. 단순 테스트 실패는 자동으로 외부 차단이 되지 않는다.

## 한 티켓의 실행 루프

1. 선행 티켓과 원본을 읽는다. 수정할 파일, 이번에 제공하는 공개 계약, 영향을 받는 소비자를 적는다.
2. 티켓의 정상·실패 조건을 재현하는 테스트를 만든다. 구현 전 의도한 RED를 확인한다. 조사·실측 티켓은 테스트 코드 대신 출처/실험 조건을 고정한다.
3. 이번 티켓의 단일 동작을 구현한다. 인접 기능까지 함께 구현해야 한다면 의존 관계와 범위를 먼저 수정한다.
4. 지정한 검증을 실제 실행한다. 명령, 입력, 환경, 기대 결과, 실제 결과, 증거를 기록한다.
5. 실패하면 재현을 고정하고 원인을 조사해 한 가설에 맞는 수정을 한다. 동일 실패 조건과 정상 조건을 다시 실행한다. 같은 조건을 재현하지 못했다면 해결로 판정하지 않는다.
6. 수정·재검증이 같은 문제에서 2회 연속 실패하면 아래 사례 조사 분기를 반드시 수행한다.
7. 직접 영향받는 소비자 회귀 테스트와 모듈화 검증을 수행한다. 실패하면 수정 단계로 돌아간다.
8. 정상·실패 조건, 회귀, 모듈화가 통과하고 미해결 결함이 없으면 증거를 채워 `done`으로 바꾼다. 모든 자식 티켓이 끝나도 태스크의 실제 통합 검증을 생략하지 않는다.

실패가 없으면 수정 루프는 `해당 없음 — 최초 검증 통과 증거`로 기록한다. 사례 조사 미발동도 실패 회차 기록을 근거로 표시한다. 체크리스트의 적용하지 않은 항목은 이유를 적고 처리 완료로 체크한다.

## 2회 실패의 의미

- 실패 회차는 **수정한 뒤 같은 문제를 재검증했으나 해결하지 못한 것**이다.
- 최초 오류 발견과 구현 전 예상 RED는 회차를 증가시키지 않는다.
- 테스트 도구·명령·티켓 이름을 바꾸어도 같은 문제라면 이력을 이어 간다. 다른 티켓에서 이어받을 때 원래 실패 기록을 링크한다.
- 정상 복구를 확인하면 연속 실패는 종료되지만 기록은 지우지 않는다. 단순히 증상을 숨기거나 테스트를 제거해 성공으로 만들지 않는다.

## 기존 해결 사례와 대안 조사

1. 저장소 코드, `git log`, 이전 티켓/증거에서 같은 오류와 이미 시도한 해결을 찾는다.
2. 공식 문서, 릴리스 노트, 공식 저장소 이슈·PR에서 오류 문구와 관련 버전으로 검색한다.
3. 필요한 경우 웹 검색, 허용된 페이지 수집/크롤링, 다른 검색 도구를 사용한다. 접근 제한을 우회하거나 무관한 데이터를 대량 수집하지 않는다.
4. 출처 URL/커밋, 해결한 버전, OS/런타임/GPU 조건, 현재 증상과의 차이를 기록한다. 기술적 해결 근거는 공식 자료·원본 코드·재현 결과로 확인한다.
5. 적용 가능한 해결책 하나를 선택해 수정하고 같은 재현 조건으로 검증한다. 원문과 맞지 않으면 채택하지 않은 이유를 적는다.
6. 사례가 없으면 최소 재현, 로그·계측, 의존 버전 비교, 다른 도구 또는 공식 우회 방식으로 가설을 좁힌다. 검색 실패만 기록하고 이전 추측 수정을 반복하지 않는다.

조사 결과가 없어도 생산적인 대안 실험은 진행한다. 제품의 확정 요구사항 변경이나 파괴적 조치를 이 규칙이 자동 승인하지는 않는다. 실제 외부 조건이 필수이면 차단/해제 조건을 기록하고 독립적으로 가능한 작업을 진행한다.

## 완료 검증과 장부 검사

`py docs/work/check_work.py`는 문서 링크, ID/선행 관계, 순환, 분할 범위, 필수 절차와 완료 증거 누락을 검사한다. 티켓의 상태는 Markdown이 원본이고 `ticket-map.json`은 구조 인덱스다. 두 곳의 의존관계가 다르면 검사에 실패한다.

이 검사는 제품 기능·테스트 출력의 진실성을 대신 검증하지 않는다. 구현 담당자는 실제 테스트 출력을 확인해야 한다. 코드 구현 전에는 예정 테스트 파일이 없어도 정상이다. CORE-03-03 이후에는 코드 변경마다 `npm run check:modules`도 실행한다.

문서 변경 후 구조 검사를 실행하고, 완료로 바꾸기 전에 해당 티켓의 실제 검증 및 모듈화 증거를 확인한다. 태스크 종료와 공개 API 변경 시 소비 모듈 통합을 다시 확인한다.
